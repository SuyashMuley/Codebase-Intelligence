# Deployment: Neon, Render, Vercel

Everything here uses free tiers. The database comes first, then the API, then the frontend; GitHub App settings are updated last because they need the final frontend URL.

**What was verified and what was not.** The backend image builds, and the container was started with production settings against a fresh pgvector database: all migrations ran and `/health` and `/ready` answered. The Neon, Render and Vercel dashboards, `render.yaml` as a blueprint, and the Vercel build were **not** run from here (no accounts). Treat those steps as a checklist to follow, and tell me where one is wrong.

## 1. Neon (Postgres with pgvector)

1. Create a project. Pick the region closest to your Render region.
2. In the SQL editor run `CREATE EXTENSION IF NOT EXISTS vector;` (the first migration also does this, but a failure here is clearer than one during deploy).
3. Copy two connection strings from the dashboard:
   - **Pooled** (host contains `-pooler`): this is `DATABASE_URL`.
   - **Direct** (no `-pooler`): this is `ALEMBIC_DATABASE_URL`. Migrations need a session, which the pooler does not give them.
4. Both must start with `postgresql+psycopg://` (replace the `postgresql://` that Neon shows) and end with `?sslmode=require`.

The free database holds 0.5 GB. A repository at the chunk cap (6,000) stores a few tens of MB with its embeddings. Disconnecting a repository deletes its data.

## 2. Render (the API)

1. Push this repository to GitHub.
2. Render, **New, Blueprint**, pick the repository. It reads `render.yaml` and asks for the variables marked `sync: false`.
3. Fill them in:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Neon pooled string |
| `ALEMBIC_DATABASE_URL` | Neon direct string |
| `APP_BASE_URL` | Your Vercel URL, for example `https://cip.vercel.app` (no trailing slash). You can use a placeholder first and fix it in step 4. |
| `CORS_ORIGINS` | The same URL |
| `GITHUB_APP_CLIENT_ID`, `GITHUB_APP_CLIENT_SECRET` | From your GitHub App ([setup](GITHUB_APP_SETUP.md)) |
| `TOKEN_ENCRYPTION_KEY` | `python3 -c "import base64, os; print(base64.urlsafe_b64encode(os.urandom(32)).decode())"`. Changing it later signs everyone out. |
| `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` | Workers AI; the token needs the Workers AI permission |
| `OPENROUTER_API_KEY` | OpenRouter key; free models need no credit |

`SESSION_SECRET` and `CLIENT_KEY_SALT` are generated by Render. `ENVIRONMENT=production`, `COOKIE_SECURE=true` and `FORWARDED_FOR_HOPS=1` are set in the file.

In production the API **refuses to start** unless the GitHub App values, `SESSION_SECRET`, `TOKEN_ENCRYPTION_KEY`, `COOKIE_SECURE=true`, an `https://` `APP_BASE_URL` and a non-default `CLIENT_KEY_SALT` are all set, and the log says which is missing.

4. Migrations run on every start (`alembic upgrade head` in the image's command). After deploy, `https://<service>.onrender.com/ready` should answer `{"status":"ready","migration":"0006"}` (the number moves with new migrations).

`https://<service>.onrender.com/docs` serves the interactive API reference (OpenAPI).

**Free-tier behaviour.** Render's free service sleeps after about 15 minutes idle; the first request afterwards can take 30 to 60 seconds, and the app says "Waking up the server" while it waits. It also restarts now and then, which is safe: the indexing job is a resumable state machine and the next `tick` continues where the last stopped. There is **no background worker**: indexing advances only while the repository page is open in a browser.

## 3. Vercel (the frontend)

1. Import the repository, set **Root Directory** to `frontend`.
2. Add the environment variable `BACKEND_URL` = `https://<service>.onrender.com` (no trailing slash). **It is read at build time** (`next.config.ts` turns it into the `/api` rewrite), so set it before the first deploy and redeploy after changing it.
3. Deploy. The browser only talks to the Vercel origin; `/api/*` is proxied to Render, which keeps the session cookie first-party and removes CORS from the picture.

This replaces the `vercel.json` rewrite the plan first described: the rewrite already lives in `next.config.ts` and is exercised by local development, so a second copy would only be able to disagree with it.

## 4. Point GitHub at production

In the GitHub App settings:
- **Callback URL**: add `https://<your-vercel-domain>/api/auth/github/callback` (keep the localhost one for development).
- **Homepage URL**: the Vercel URL.

Then set `APP_BASE_URL` and `CORS_ORIGINS` on Render to the final Vercel URL if you used a placeholder, and let it redeploy.

## 5. Check it works

1. Open the Vercel URL. You should land on the sign-in page.
2. Sign in with GitHub. If you come back to the login page, the callback URL or `APP_BASE_URL` is wrong (they must match exactly), or cookies are not Secure.
3. Connect `pallets/click`, index it (keep the tab open), and ask a question on the Ask tab. [DEMO.md](DEMO.md) has a script.

## Limits worth knowing

| Resource | Free allowance | Where the app stops |
| --- | --- | --- |
| Cloudflare Workers AI | 10,000 neurons a day, about 0.9 per chunk | indexing's embed phase reports `quota_exceeded` and resumes the next day |
| OpenRouter free models | roughly 50 requests a day without credit, with per-minute limits | Ask and AI review say the model is busy; failures are not charged to the user's daily 25 |
| GitHub API | 5,000 requests an hour per signed-in user | a rate-limit wait without using an attempt |
| Neon | 0.5 GB | writes fail; disconnect repositories you no longer need |
| Render | one instance, sleeps when idle | the in-process rate limiter assumes a single instance (see M10 in the plan for scaling out) |

## Rotating secrets

- `SESSION_SECRET`: changing it invalidates in-flight sign-ins only.
- `TOKEN_ENCRYPTION_KEY`: changing it signs every user out (stored tokens cannot be decrypted); they sign in again.
- GitHub client secret: generate a new one in the app settings, update Render, then delete the old one.
